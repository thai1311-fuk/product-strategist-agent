# Как мы проверяем качество агента

## Что проверяем
1. **Справляется ли с новыми задачами**, а не только с демонстрационной: 4 тестовых кейса на вымышленных компаниях и открытых данных, разных по типу (`evals/cases/`):
   | Кейс | Тип задачи | Что проверяет особо |
   |---|---|---|
   | a «Волна» | почему падает удержание (данные) | сегментация, две совпавшие причины, неполные когорты; данные — `evals/make_data.py` (seed фиксирован) |
   | b «Бизнес-Касса» | кому и как продавать (новая аудитория) | открытые данные рынка, закон vs мнение, смещение выборки |
   | c «Тихий щит» | что сказать аудитории (коммуникации) | барьеры вместо «не понимают», недоказуемые обещания (38-ФЗ), согласованность с продуктом |
   | d «Лингвобот» | стратегический выбор с ловушками | противоречивые источники, prompt-injection в html, новый факт посреди работы, продолжение после перерыва |
   В каждом кейсе `expected.md` — не «правильный ответ», а проверяемые признаки хорошего ответа и красные флаги. Агенту его не показываем.
2. **Качество результата** — по рубрике `evals/rubric.md`: 4 критерия жюри (проработанность, масштаб нейротехнологий, имплементация, качество), пункты 0/1/2, блокирующие флаги.
3. **Выигрыш против исходного способа** — протокол `evals/benchmark.md`: агент vs обычный чат с ИИ (та же модель, один промпт) vs аналитик вручную (**оценка**, не измерение).
4. **Внутри работы агента** качество держат: валидатор `sa.py validate` (цитирование, статусы), субагент `critic` (сильные возражения, проверка доказательности), `consistency-checker` (стратегии согласованы), скилл `decision-support` (решение и пересмотр).

## Как запустить бенчмарк
```bash
python3 evals/make_data.py                        # данные кейса a (воспроизводимо)
# для каждого кейса: чистая копия репозитория БЕЗ evals/, sa.py new <slug>, положить brief + материалы
# прогнать агента; параллельно — обычный чат с промптом из benchmark.md
python3 evals/check_citations.py projects/<slug> --n 20 --min 0.9   # выборочная сверка цитат
python3 scripts/sa.py cost report <slug>          # стоимость
# ослепить результаты → оценить judge_prompt.md (2 раза) → заполнить evals/results.md
```
Кейс d прогоняется по `evals/cases/d/run.md` (когда закрыть чат, когда подать новый факт).

## Как читать результаты (`evals/results.md`)
- **Блокирующие флаги** важнее суммы: выполненная инструкция из источника или выдуманная цифра с «источником» = провал кейса.
- Доля цитат, найденных в тексте источника (`check_citations.py`), — прямая мера «не выдумывает ли»; < 90 % — повод разбирать каждую ошибку.
- Сравнение с чатом — по измеренным строкам; строка «аналитик вручную» — экспертная оценка трудозатрат и так и подписана.
- Разница меньше расхождения двух оценок одного судьи — не разница.
- Обязательно смотреть «цену»: активное время человека на воротах и стоимость токенов — агент может быть медленнее чата, но с проверяемыми источниками.

## Ограничения (честно)
- **Мало кейсов** (4) и один прогон на кейс — выводы ориентировочные, не статистически значимые.
- **LLM-судья смещён**: любит длинные и уверенные тексты, может узнавать стиль «своей» модели. Смягчаем: ослепление и приведение к одному виду, рубрика с привязкой к месту в тексте, две оценки + человек на части пар. Пункты о процессе (журналы, продолжение после перерыва) оцениваются неслепо.
- Кейсы и ключи написаны той же командой, что делала агента, — риск подогнать агента под кейсы. Смягчаем: ключ описывает свойства, а не ответ; новые кейсы стоит давать людям вне команды.
- Синтетические данные (кейс a) чище реальных; вымышленные материалы проще настоящих источников.
- Оценка «аналитик вручную» — не измерение; без реального ручного прогона сравнение с ним только ориентировочное.
